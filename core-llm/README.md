# core-llm — слой выбора сценария

Самостоятельное ядро маршрутизатора Voice Router: **транскрибированный текст → LLM (через OpenRouter) → сценарии с процентами**.
Ничего лишнего: модель отвечает одной строкой вида `SC27:95 SC04:90` — только ID из каталога и уверенность в процентах,
только те сценарии, где уверенность > 0. Никаких JSON, пояснений и рассуждений — поэтому ответ занимает ~6 токенов.

```
python3 router.py "Хочу продлить ОГПО и заодно добавить в него сына"
→ SC27:95 SC04:95   (primary SC27, intents [SC27, SC04], status route, ~450 мс)
```

## Файлы

| Файл | Что это |
|---|---|
| `scenarios.index.txt` | «Выжимка» каталога: 40 сценариев + 3 системных намерения, по одной строке на сценарий — `ID \| смысл \| ru-маркеры \| kk-маркеры \| ≠ границы с соседями`, плюс блок разводки самых путаемых групп. Собрана вручную из `data/scenarios.json` (description, not_this_if, examples). Это единственное, что модель знает о сценариях. |
| `prompt.md` | Системный промпт: формат ответа, семантика процентов, правила мульти-интента, системных намерений и контекста диалога. |
| `router.py` | Ядро: собирает system = `prompt.md` + `scenarios.index.txt`, шлёт запрос, парсит пары, применяет политику решения. CLI + оценка на dev-наборе и диалогах + бенчмарк моделей. Только стандартная библиотека Python. |
| `.env.example` | Переменные окружения. Ключ кладётся в `core-llm/.env` (в git не попадает). |

## Запуск

```bash
cp core-llm/.env.example core-llm/.env      # вписать OPENROUTER_API_KEY
python3 core-llm/router.py "Кеше аварияға түстім, но я не виноват, виновник у вас застрахован"
python3 core-llm/router.py --raw "Алло, я по поводу страховки"          # только строка модели
python3 core-llm/router.py --eval                                        # dev_utterances.json → метрики + predictions
python3 data/evaluate.py core-llm/reports/predictions-google_gemini-2.5-flash-lite.json data/dev_utterances.json
python3 core-llm/router.py --dialogs                                     # dialogs_sample.json, реплика за репликой с контекстом
python3 core-llm/router.py --bench google/gemini-2.5-flash-lite,openai/gpt-4.1-mini   # сравнить модели
```

С контекстом диалога (то, что backend знает о сессии):

```bash
python3 core-llm/router.py --prev "SC17|Здравствуйте, что с моим заявлением по каско" \
  --bot "Заявление на рассмотрении, решение до 9 октября." --active SC17 \
  "А по заявлению мне что-то ещё нужно донести?"
```

Из Python:

```python
from router import Router
r = Router()                      # модель и ключ из .env
r.warmup()                        # прогрев соединения и кэша промпта — один раз при старте
res = r.route("Полис на почту не пришёл, и заодно скажите, до какого числа он действует")
res["primary"], res["predicted"], res["status"], res["scenarios"], res["language"], res["route_ms"]
# 'SC26', ['SC26', 'SC25'], 'route', [{'id':'SC26','pct':95,...},{'id':'SC25','pct':90,...}], 'ru', 447.2
```

## Формат ответа модели и политика решения

Модель возвращает независимые проценты (не обязаны суммироваться в 100): 70–100 — сценарий запрошен, 1–10 — альтернативное
прочтение, которое клиент не просил, ~55/45 — один запрос, реально неоднозначный между двумя сценариями.
Порядок пар = порядок обработки: срочные (SC11, SC15, SC38) первыми, дальше как клиент сказал.

Политика (`Router.decide`, пороги в `.env`):

| Условие | Результат |
|---|---|
| первая пара ≥ `ROUTER_SECOND_THRESHOLD` (20) | `primary` |
| primary ≥ `ROUTER_THRESHOLD` (60) | `status=route`; остальные бизнес-пары ≥ 20 — дополнительные намерения (`intents`, `predicted`) |
| primary < 60 или `SYS_UNCLEAR` | `status=clarify`; `predicted=[primary]`, остальные пары — варианты для уточняющего вопроса |
| `SYS_GREETING` | `greeting`; только приветствие без запроса, локализованный ответ формирует frontend |
| `SYS_OUT_OF_SCOPE` / `SYS_GOODBYE` / `SC37` | `out_of_scope` / `goodbye` / `handoff` |

`predicted` — ровно то, что ждёт `data/evaluate.py` (`{"U001": ["SC01"], "U081": ["SC27", "SC04"]}`).
`language` (ru / kk / mixed) считается локально по казахским буквам и русским служебным словам — 0 мс, 104/104 на dev-наборе.

## Результаты

Модель по умолчанию — **`google/gemini-2.5-flash-lite`** (OpenRouter, provider sort = latency).

Dev-набор организаторов, `data/evaluate.py` (104 реплики: 52 ru / 45 kk / 7 mixed; 84 single, 13 multi-intent, 4 out-of-scope, 3 unclear):

| метрика | значение |
|---|---|
| primary_accuracy | **1.000** |
| full_match | **1.000** |
| intent_recall (multi-intent) | **1.000** |
| язык (ru/kk/mixed) | 1.000 |
| latency выбора сценария, p50 / p95 | **457 мс / 617 мс** (последовательные вызовы, тёплое соединение) |
| доля ≤ 500 мс | 75 % |
| prompt tokens | ~5 800, из них ~75 % из кэша провайдера при последовательных вызовах |
| стоимость 104 реплик | ≈ $0.05 |

`dialogs_sample.json` (40 клиентских реплик с контекстом — смена темы, возврат, смешанная речь, подтверждения):
primary 0.975, full match 0.95. Две известные промашки: возврат к прерванной теме с вопросом о документах
(модель добавляет старый SC17 к верному SC18) и «номер телефона + соедините с человеком» (к SC37 добавляет SC35).

Задержка измерена с этой машины через OpenRouter; базовый RTT до провайдера ≈ 450 мс — сам prefill 5.8k токенов
добавляет ~100 мс, декод 6 токенов — десятки мс. То есть быстрее уже почти некуда без смены сетевого пути.

## Почему это быстро

1. **Индекс вместо каталога.** В промпт идёт не `scenarios.json` (90 КБ), а его выжимка: смысл, маркеры на двух языках и
   границы `not_this_if`. Ответные шаблоны, слоты, actions — не нужны для выбора и не тратят ни токены, ни внимание модели.
2. **Выход ~6 токенов.** Нет JSON, нет полей `reason`/`alternatives` текстом — только `ID:PERCENT`. Декод — десятки миллисекунд.
   Объяснение для панели супервизора строится детерминированно: имена сценариев, проценты, альтернативы, пороги.
3. **Стабильный префикс.** system-промпт байт-в-байт одинаков между запросами → prompt caching у провайдера (видно в `cached_tokens`).
4. **Keep-alive.** Одно HTTPS-соединение на поток, без TLS-рукопожатия на каждый запрос; `warmup()` при старте.
5. **`temperature=0`, `max_tokens=64`, `reasoning` выключен**, provider sort по latency в OpenRouter.

## Интеграция в Go backend

Всё, что нужно бэкенду, — это два текстовых файла и одна политика:

- system = содержимое `prompt.md` + `\n\n` + `scenarios.index.txt`; user = `CLIENT: <текст>` (или блок `CONTEXT:` как в `Router.build_user`);
- `POST https://openrouter.ai/api/v1/chat/completions` с `{"model", "messages", "temperature": 0, "max_tokens": 64,
  "reasoning": {"enabled": false}, "provider": {"sort": "latency"}}`;
- ответ парсится регуляркой `(SC\d{2}|SYS_[A-Z_]+):(\d{1,3})`, дальше политика из таблицы выше.

## Ограничения

- Dev-набор — не набор жюри; 100 % на нём означает «правила границ работают», а не «ошибок не будет».
- Маленькие модели чувствительны к формулировкам промпта: изменения `prompt.md` нужно перепроверять `--eval` и `--dialogs`
  (ответы детерминированы при `temperature=0`, поэтому одного прогона достаточно).
- Задержка зависит от сети до OpenRouter и провайдера; цифры выше — с одной машины, не гарантия.
- Ядро не извлекает слоты и не генерирует ответ — только выбор сценария; ответные шаблоны берутся из каталога на стороне backend.

## Подключённый frontend

Запустите `python3 core-llm/server.py` из корня репозитория. Сервис использует тот же `Router`,
промпт, индекс и `.env`, что CLI. `GET /healthz` проверяет запуск; `POST /api/route` принимает
`{text, history?: [{text, scenario}], active?, last_bot?}` и возвращает исходный результат `Router.route`.
По умолчанию слушает только `127.0.0.1:8090`; в Docker доступен только внутри сети Compose.

В frontend выберите **LLM**. Next.js проксирует `/api/core-route` в Python через серверную
переменную `CORE_LLM_URL`. Ключ OpenRouter браузеру не передаётся. Контекст передаётся для каждой
реплики, действия выполняются на синтетических данных frontend. Объяснение в трассировке
детерминированно составляется из результата модели, а не выдаётся за рассуждения LLM.
Ошибки ядра показываются пользователю без незаметного переключения на лексический роутер.

Проверки без ключа: `python3 -m unittest discover -s core-llm -p 'test_*.py'`.
Полная инструкция ручного и Docker-запуска — в корневом README.
